# Embedding This MCP Server

This document is for a host application that wants to run this repository's MCP server—OAuth, session authentication, and the `/mcp` transport—inside a larger application rather than as its own standalone deployment. It covers three scenarios: running alongside a sibling Bun application in this monorepo, mounting inside a SvelteKit application via its `handle` hook, and the environment variables and URL paths an embedding host must account for either way.

## Running alongside a sibling application in this monorepo

### The database

`packages/database` owns every migration. A sibling application must never write its own migration against the tables this package defines—`packages/database/drizzle/` is the single source of truth for schema changes—applied either through `packages/database/src/migrate.ts`'s `runMigrations()` or through the `drizzle-kit migrate` CLI that `packages/database/package.json`'s `db:migrate` script invokes—and that migration history is the single source of truth for what the auth database looks like. A sibling application that needs its own tables should own a separate migration path against the same Postgres instance, not append to this package's migration directory.

A separate directory alone is not enough, and getting this wrong fails silently. Drizzle records applied migrations in one table, `drizzle.__drizzle_migrations` by default, and its `neon-http` migrator decides what is pending from the single newest `created_at` in that table rather than per-file content hashes (the same mechanic `packages/database/CLAUDE.md` documents for baselining). Point two independent histories at that one default table and whichever has the older timestamps gets skipped wholesale—the migrator reports success while the auth schema, or the sibling's own schema, is quietly left behind. A sibling must therefore isolate its migration metadata as well as its migration files, by passing a distinct `migrationsTable` and `migrationsSchema` in its own `migrate()` call. Verify it before trusting a deployment: the sibling's metadata table should exist under its own name, and `drizzle.__drizzle_migrations` should contain only this package's history.

For the database _connection_ itself, two options exist depending on how tightly the sibling application wants to couple to this package's own client lifecycle. `packages/database/src/index.ts` exports a ready-made `database` client. It is a lazy `Proxy`: the underlying Drizzle client is constructed on first property access, not at module load. What _does_ happen at module load is this package's `env.ts` validation—importing the module at all validates `DATABASE_URL` and throws if it is missing—so a sibling application that imports it inherits this package's environment contract immediately, and its connection strategy on first use. The alternative, added for exactly this embedding case, is `packages/database/src/create-database-client.ts`, exported as `@template/database/create-database-client`: a driver-agnostic factory, `createDatabaseClient(connection)`, that takes a caller-supplied `NeonQueryFunction` (Neon's SQL-over-HTTP driver, for a request-scoped caller) or a `Pool` (`@neondatabase/serverless`'s own connection pool, which speaks the Postgres wire protocol over a WebSocket to Neon rather than opening a direct TCP connection, for a long-lived process) and returns a `drizzle`-wrapped client against the same `schema`, without importing this package's own `env.ts` or constructing a connection itself. A sibling application that already manages its own Postgres connection pooling—because it targets a different deployment shape, or needs a connection lifecycle this package's `env.ts`-driven singleton doesn't offer—should build its own `NeonQueryFunction` or `Pool` and pass it to `createDatabaseClient` rather than importing the pre-built `database` singleton and its implicit environment coupling.

Either way, both this server and the sibling application are reading and writing the same `schema` (`packages/database/src/schema.ts`) against the same Postgres database. That schema includes the OAuth client, grant, and session tables this server's authentication flow depends on—a sibling application that only needs read access to, say, the user table for its own unrelated purposes is fine; a sibling application that writes to the session or grant tables outside this server's own code paths is not a supported scenario and will produce state this server's authentication logic doesn't expect.

### Sharing Cinder tokens

Both `applications/web/package.json` and `packages/mcp-apps/package.json` pin `@lostgradient/cinder` to the identical version specifier (`^0.24.8` as of this writing), and the root `package.json`'s `overrides` block pins the resolved version centrally so every consumer in the workspace—including a sibling application added later—resolves to the same installed copy rather than two independent instances of the design system. A sibling application sharing this server's UI surface (the consent screen, the account page) should consume the same `@lostgradient/cinder` design tokens rather than reimplementing them, both for visual consistency and so token updates only need to happen in one place.

### Sharing an authenticated session, and why the obvious recipe does not work

The intuitive approach—give both applications the same `SESSION_SIGNING_SECRET` and `SESSION_COOKIE_NAME`, widen the cookie domain, get single sign-on—does not work here, for two independent reasons worth stating plainly before anyone builds on it.

The session cookie is not signed. `applications/web/src/lib/session-authentication.ts` mints an opaque random token (`randomBytes(48)`) and stores only its hash in `user_sessions`; hydration is a database lookup against that hash. `SESSION_SIGNING_SECRET` is not involved. That secret signs CSRF tokens (`applications/web/src/lib/csrf-protection.ts`) and the Google sign-in state, so sharing it buys a sibling application nothing where session hydration is concerned—and sharing a signing secret that is _not_ needed only widens the blast radius of a leak.

In production the cookie cannot be widened to another host at all. `session-authentication.ts` emits it with the `__Host-` prefix, and browsers accept a `__Host-` cookie only when it is `Secure`, has `Path=/`, and carries **no** `Domain` attribute. That last requirement is the whole point of the prefix: it pins the cookie to the exact host that issued it. There is no cookie-domain configuration that shares a `__Host-` cookie across `app.internal` and `mcp.internal`, and removing the prefix to permit one would give up the host-pinning that makes the cookie resistant to subdomain-takeover attacks.

What this leaves is one supported shape and one design decision. Supported: a sibling application served from the **same host** as this server (the same origin, different paths), which sees the same cookie and can hydrate a session by looking up its hash through the shared `user_sessions` table—reusing this server's own `hydrateSession`, published as `@template/web/lib/session-authentication`, rather than reimplementing a security-sensitive lookup. Not supported without new design work: cross-subdomain or cross-origin single sign-on, which needs a deliberate mechanism this server does not currently have—an OAuth flow against this server (which it already implements, and is the intended path for a separate application), or a purpose-built cross-domain token exchange. Reach for the OAuth flow before inventing the token exchange.

The caveat that does survive: any sibling application reading `user_sessions` directly shares this server's session contract, so a validation gap in either codebase is a gap in both. That is a reason to prefer the OAuth path for anything that is genuinely a separate application.

## Embedding inside a SvelteKit application

### The mount seam

`applications/web/src/application.ts` exports `handleApplicationRequest(request, input?)`, which by default also serves this server's own static assets (`/assets/*` and `/favicon.png`) from its own build output. A host already has its own static-asset story and does not want this server competing for those paths. `applications/web/src/application-mount.ts` exports the seam built for exactly this, published as `@template/web/application-mount`:

```ts
const mount = await createApplicationMount({ serveStaticAssets: false });
// mount.handleRequest(request, { clientAddress }) => Promise<Response>
// mount.assetManifest => { stylesheetPath, clientBundlePath, clientSourceMapPath }
// mount.dispose() => Promise<void>
```

It is an async lifecycle rather than a handler factory, and that distinction is load-bearing. `applications/web/src/server.ts` is the only other runtime entry point, and it does three things at startup besides dispatching requests. An embedding host that received only a dispatcher would skip all three, each failing silently:

- **Production invariants**: `assertProductionStartupInvariants()` (`applications/web/src/lib/startup-invariants.ts`) is what refuses to boot a production process with insecure database transport, a missing `REDIS_URL`, absent trusted-proxy configuration, or an invalid `BASE_URL`. Skipping it lets an embedded production deployment run in configurations the standalone server explicitly rejects.
- **The asset manifest**: `loadAssetManifest()` populates the cache `getAssetManifest()` reads. Without it that accessor returns the unhashed development fallbacks (`/assets/application.css`, `/assets/client.js`) while `applications/web/src/build.ts` publishes only hash-named files—so the consent and legal pages render unstyled and the home page never hydrates, with nothing in the logs to explain why.
- **Scheduled cleanup**: `startScheduledCleanup()` is the only in-process sweep of expired authorization codes, tokens, authorization transactions, and revoked sessions. Without it those rows accumulate indefinitely.

`createApplicationMount()` performs all three, in that order, and fails fast: if the invariant check throws, no timer has been started and no manifest loaded.

`dispose()` mirrors `server.ts`'s graceful shutdown for the parts a host cannot reach itself—it stops the cleanup interval, waits for any sweep already mid-flight (clearing an interval stops future ticks, not the one currently issuing database writes), calls `shutdownMcpTransports()` (a `subscriptions/listen` response stays open until it does), and closes the Redis client. After disposal `handleRequest` answers `503` rather than dispatching, so a stale routing hook cannot rebuild the very state teardown just released. Concurrent callers all await the same teardown rather than the second one returning early while the first is still draining, so a host may safely call it from more than one shutdown path. A host that restarts without calling it drops active MCP streams instead of draining them.

Exactly one mount may exist per process, and both illegal transitions throw rather than degrading quietly. A second `createApplicationMount()` while one is live is refused, because two handles would share one cleanup timer, MCP handler cache, grant-revocation subscriber, and Redis client—disposing either would break the other. The claim is taken synchronously before the first `await`, so two callers racing the factory cannot both get a handle. Disposal is likewise permanent, and calling the factory again afterward throws. This is deliberate: tearing the mount down clears module-scoped state in `applications/web/src/lib/mcp-handler.ts` that only initializes once per process—the user-handler idle-eviction timer, and the Redis subscription behind cross-replica grant revocation, whose latch stays set after the subscriber disconnects. A second mount would run without either, silently, so it is refused instead.

That module-scoped state is established when `mcp-handler.ts` is _evaluated_, which happens as soon as anything imports the mount—before `createApplicationMount()` runs its first check. So if startup fails, the mount releases that state before the rejection propagates, rather than leaving a host that catches the error and keeps running with an orphaned timer and Redis subscriber it has no handle to close. The consequence worth knowing: a failed mount cannot be retried in the same process, because what it would need has already been torn down. Fix the configuration and start a new process.

The host keeps ownership of its own socket: the mount never binds a port, never installs a signal handler, and never calls `process.exit`. Draining in-flight requests before `dispose()` is the host's job, since only the host knows when its server stopped accepting them.

### Serving the generated assets

Turning off this server's static-asset serving does not make the assets unnecessary—the HTML it renders still references the hash-named files `applications/web/src/build.ts` emits into `applications/web/public/assets`. A host's own static pipeline does not contain that directory automatically, so a host that neither copies those files nor asks the mount to serve them gets a 404 for every asset, unstyled pages, and no hydration.

There are two supported answers. Either copy the built contents of `applications/web/public/assets` into whatever the host serves at `/assets/*` as part of its own build—along with `favicon.png` and `robots.txt` at the root—using `mount.assetManifest` to know the exact hashed paths the rendered HTML will ask for; or pass `serveStaticAssets: true` and let the mount serve all three, which is the simpler option when the host has no strong opinion and no CDN in front.

`robots.txt` is easy to forget and worth not forgetting: it is what keeps crawlers out of `/oauth/`, `/mcp`, `/auth/`, and `/health`, so an embedded deployment that drops it quietly exposes those paths to indexing.

### A limitation worth knowing before you start

`applications/web/package.json` publishes `./application-mount` as TypeScript source, and that source imports `@web/application`, `@web/env`, and other `@web/*` paths. That alias is defined only in `applications/web/tsconfig.json`, and a consuming project's resolver does not inherit path mappings from a dependency's tsconfig. There is no bundled entry point today, so importing `@template/web/application-mount` fails on its first internal import unless the host's own resolver is told how to resolve the alias—mapping `@web/*` to `applications/web/src/*` in the host's `tsconfig.json` `paths` and, for a Vite-based host, in `resolve.alias` as well.

That is a real constraint, not a formality: it applies to a sibling application in this monorepo just as much as to an external host, because no root `tsconfig.json` defines the alias either. Publishing a bundled entry point with package-relative imports is the durable fix, and is the thing to do if this seam ever needs to be consumed outside this repository.

`clientAddress` sits on `handleRequest`'s per-call input rather than on the factory, because it is per-request state a host only knows once a request arrives (`Bun.serve`'s `server.requestIP(request)`, a SvelteKit host's `event.getClientAddress()`). Passing it is what keeps rate-limiting identity and trusted-proxy handling correct; omitting it makes every caller look like one unknown client.

From a SvelteKit `handle` hook, construct the mount once at module scope (never per request), await it before serving traffic, call `mount.handleRequest` for any path this server owns and return its `Response` directly instead of calling `resolve`, and wire `mount.dispose()` into the host's shutdown path. Requests to your own routes fall through to `resolve` as normal.

Note that `@web/*` is this codebase's internal TypeScript path alias, not what an external host imports; the package `name` is `@template/web`, so a host imports `@template/web/application-mount`.

### Four real constraints

The bundler and loader situation is empirically verified, not assumed. This server's `packages/mcp/src/server.ts` imports its tool instructions with `import instructions from './instructions.md' with { type: 'text' }`—an import-attribute form Bun's loader understands natively. Building the same shape through Vite fails outright. This was checked by reproducing the import shape in standalone scratch projects outside this repository—this repository has no Vite dependency, no `vite.config.*`, and no fixture reproducing it, so the experiment is not re-runnable from a checkout—against both `vite@5.4.21` (Rollup) and `vite@8.2.2` (Rolldown). In both, `vite build --ssr` on this exact import shape throws immediately, because Vite ignores the `with { type: 'text' }` attribute and tries to parse the markdown file's contents as JavaScript. Marking the containing package `ssr.external` does not fix this at build time either—with `DEBUG=vite:*` confirming the exclusion was correctly applied, the build still failed, because Vite/Rollup still descends into and parses an externalized package's source during an SSR build; only a true Rollup-level `external` (not merely `ssr.external`) leaves the import untouched in the emitted bundle, and even then the import only succeeds at runtime if the process executing the built output is Bun, since Node has no native handler for `.md` plus `with { type: 'text' }`. A SvelteKit host built and deployed through Vite's SSR build, then executed under Node, cannot import this package's code that uses this pattern without hitting exactly this failure. `applications/web` itself has no `vite.config.*` or SvelteKit dependency today—it is a Bun-native SSR application, not a SvelteKit host—so this constraint applies to the _embedding SvelteKit application's_ build pipeline, not to this repository's own build.

The process this server runs in must be long-lived, not a request-scoped edge or serverless function. `applications/web/src/lib/mcp-handler.ts` keeps a per-user, in-process handler cache (`McpUserHandlerCache`) so that a user's `subscriptions/listen` stream and the connection state backing it survive across requests within one process. Redis (`mcp-user-event-bus.ts`) is what makes cross-replica delivery correct when more than one instance of this process is running—a `publish()` call fans out over Redis regardless of which instance holds a given user's open stream—but Redis is fan-out between already-running long-lived processes, not a substitute for one. An edge or serverless adapter that tears the process down between requests has no in-process cache left for the next request to find, so the per-user connection state this server depends on for `subscriptions/listen` would not survive.

Importing `applications/web`'s own `env.ts` or `packages/database`'s `env.ts` triggers environment validation immediately, at import time, before any request handling begins: each validates its own environment at module scope, deliberately with no default for `NODE_ENV`. An embedding host must have every variable those two schemas require set _before_ it ever imports those modules, not merely before it starts serving requests.

`packages/mcp` deliberately does not behave this way. Importing any of its entry points reads nothing from `process.env` and cannot throw, whatever the ambient environment—a library that validates its host's environment during module evaluation cannot be consumed, because the host can neither catch it nor supply a different environment nor decide whether it wants a server at all. Validation happens on the first call to `getEnvironment()`, which in practice is the first log line or the first `createMcpServer(...)`. A host that does not want `process.env` consulted at all can call `parseMcpServerEnvironment(env)` with its own record instead.

The OAuth discovery paths must live at the origin root. `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource` (and its `/mcp` variant) are fixed, well-known paths per the OAuth metadata specifications this server implements—they cannot be reached through a prefix like `/mcp-server/.well-known/...` and still be discoverable by a standard OAuth client. A host embedding this server under a path prefix for its other routes must still cede the literal `/.well-known/*` paths at the origin root to this server, rather than trying to prefix them alongside everything else.

## Environment variables

Every variable below is read at import time or startup time by one of this server's packages; an embedding host sets these in the process environment before importing any of this repository's code.

Tier one—required at module-import time in every environment, no default and no way to skip:

| Variable       | Owning package                                                      | What breaks without it                                                                                                                                                                                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL` | `packages/database`                                                 | `env.ts` calls `environmentalist.sync({...})` at module scope with `z.string().min(1)` and no default—importing this module with it unset throws immediately, in every `NODE_ENV`.                                                                                                                                                                           |
| `NODE_ENV`     | `packages/mcp` and `applications/web` (each validates its own copy) | `z.enum(['development', 'production', 'test'])` with deliberately no default. `applications/web` throws at module-import time. `packages/mcp` does not throw on import—it throws on the first `getEnvironment()` call (first log line or first `createMcpServer(...)`), so the variable is still required, just enforced at first use rather than at import. |

All three `env.ts` files (`applications/web`, `packages/mcp`, `packages/database`) additionally reject `SKIP_ENV_VALIDATION` if it is set to any truthy value—it is not a usable escape hatch in any environment. `applications/web` and `packages/database` throw at module scope; `packages/mcp` refuses it inside `parseMcpServerEnvironment`, so the rejection happens on first use rather than on import, but it is not skippable either way. All three also treat an empty-string value as unset, so setting a variable to `""` is still the same as not setting it. (`applications/web` and `packages/database` use `@lostgradient/environmentalist`, which has no built-in option for this and so strips empty-string entries by hand; `packages/mcp` no longer depends on Environmentalist at all and does the same stripping in its own parser.)

Tier two—only enforced when `NODE_ENV=production`, by `assertProductionStartupInvariants` in `applications/web/src/lib/startup-invariants.ts` (which collects its failures from `collectProductionStartupFailures` in `applications/web/src/lib/production-startup-requirements.ts`), called once from `server.ts` before the server accepts traffic (two exceptions noted below run outside that function):

| Variable                                         | What breaks without it in production                                                                                                                                                                  |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BASE_URL`                                       | Must be set, `https://`, and a bare origin with no path, query, fragment, or userinfo—every endpoint path is concatenated onto it directly.                                                           |
| `REDIS_URL`                                      | Must be set and, in production, use `rediss://` on a non-loopback host with no placeholder credentials. See the Redis section below for what degrades, versus what refuses to boot, when it's absent. |
| `TRUSTED_PROXY_CIDRS` and `TRUSTED_PROXY_HEADER` | Must both be set together, and `TRUSTED_PROXY_CIDRS` must parse to at least one valid CIDR entry.                                                                                                     |
| `TRUSTED_PROXY_HOP_COUNT`                        | If set, must be a positive integer string.                                                                                                                                                            |
| `DATABASE_URL`                                   | Must have a non-loopback host, a `postgres:`/`postgresql:` scheme, `sslmode=verify-full`, and no placeholder credentials.                                                                             |
| `DATABASE_URL_UNPOOLED`                          | Same checks as `DATABASE_URL`, if set.                                                                                                                                                                |
| `DATABASE_LOCAL_PROXY_URL`                       | Must be absent in production—its mere presence is itself a startup failure.                                                                                                                           |
| `SESSION_SIGNING_SECRET`                         | Must be set—checked both here (for a readable diagnostic) and independently, at module-import time, by `session-signing-secret.ts`.                                                                   |
| `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`    | Both required—there is no other production sign-in path, and `/auth/dev/login` 404s outside development.                                                                                              |
| `MCP_CONFORMANCE_MODE`                           | Must be false or unset in production—`true` registers a synthetic conformance-fixture registry outside normal scope checks.                                                                           |
| `MCP_ALLOWED_ORIGINS`                            | If set, every entry must canonicalize to a valid browser Origin shape.                                                                                                                                |
| `NODE_TLS_REJECT_UNAUTHORIZED`                   | Must not be `"0"`—that value silently defeats every TLS check listed above at the transport layer.                                                                                                    |

Separately, `packages/mcp/src/env.ts` throws from `parseMcpServerEnvironment`, outside the function above, if `NODE_ENV` is `production` and `LOG_CONTENT_DIAGNOSTICS_UNTIL` is set at all, regardless of its value. Because that package parses lazily, this fires on the first `getEnvironment()` call rather than at import—so a production host reaches it as soon as anything logs, not before it has imported anything.

Tier three—optional, defaulted, safe to omit for a minimal embedding: every `RATE_LIMIT_*_MAX` and `*_WINDOW_SECONDS` pair, `SESSION_COOKIE_NAME` (`application_session`), `SESSION_TIME_TO_LIVE_SECONDS` (2,592,000), `MCP_ALLOWED_ORIGINS` (`http://localhost:3000`), `MCP_ENABLE_UI_EXTENSION` and `MCP_CONFORMANCE_MODE` (both `false`), `MCP_TOKEN_TTL_SECONDS` (3600), `MCP_REFRESH_TOKEN_TTL_SECONDS` (2,592,000), `PORT` (3000), `HEALTH_READINESS_CACHE_TTL_SECONDS` (2), `SCHEDULED_CLEANUP_INTERVAL_SECONDS` (3600), `MCP_SERVER_NAME` (`template-mcp-server`, `packages/mcp`), `TRUSTED_PROXY_HOP_COUNT` (1), `PROTOKIT_TUNNEL_ACTIVE` (`false`), and `LOG_LEVEL` (`info`). Fully optional with no default at all: `DATABASE_URL_UNPOOLED`, `DATABASE_LOCAL_PROXY_URL`, `SESSION_SIGNING_SECRET_PREVIOUS`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (outside production), `RATE_LIMIT_KEY_NAMESPACE`, `TRUSTED_PROXY_CIDRS`/`TRUSTED_PROXY_HEADER` (outside production), `METRICS_API_KEY`, `HEALTH_READINESS_API_KEY`, `INSTANCE_IDENTIFIER`, `SERVER_BIND_ADDRESS`, `SUPPORT_CONTACT_EMAIL`, `NODE_TLS_REJECT_UNAUTHORIZED` (outside production), and `LOG_CONTENT_DIAGNOSTICS_UNTIL` (`packages/mcp`, outside production).

Two of those defaults are security-relevant rather than merely cosmetic, and an embedding host should set them deliberately rather than inherit them by omission. `PROTOKIT_TUNNEL_ACTIVE` is what closes the development sign-in bypass: `applications/web/src/routes/development-authentication-routes.ts` 404s `/auth/dev/login` whenever it is true, deliberately regardless of `NODE_ENV`, because a tunnel exposes every route to the public internet while `NODE_ENV` stays `development`. It also suppresses conformance-fixture registration in `applications/web/src/lib/mcp-handler.ts`. A host that exposes this server through any public tunnel while running outside production must set it to `true`. `INSTANCE_IDENTIFIER` is unset by default and only affects instance labelling in logs and metrics (`applications/web/src/lib/instance-identifier.ts`), which matters once more than one replica is running.

One naming mismatch is worth getting right the first time: `applications/web/src/env.ts` reads two schema fields, `RAILWAY_REPLICA_IDENTIFIER` and `HOSTNAME_IDENTIFIER` (exposed as `environment.railwayReplicaIdentifier`/`environment.hostnameIdentifier`), but those are not the names of the environment variables a host actually sets. `env.ts` derives them from real process variables before handing the environment to the resolver—`RAILWAY_REPLICA_IDENTIFIER` from `process.env.RAILWAY_REPLICA_ID ?? process.env.RAILWAY_INSTANCE_ID`, `HOSTNAME_IDENTIFIER` from `process.env.HOSTNAME`—so an embedding host that wants instance identification to work sets `RAILWAY_REPLICA_ID`, `RAILWAY_INSTANCE_ID`, or `HOSTNAME`, not the `*_IDENTIFIER` names that appear in the schema itself.

### Redis: degradation versus outright refusal

`isRedisConfigured()` is simply whether `REDIS_URL` is set. Its absence has different consequences depending on where it shows up. In rate limiting (`request-rate-limiter.ts`), if Redis isn't configured and `NODE_ENV` isn't `production`, rate limiting falls back to an in-memory per-process sliding-window store and logs one warning; if `NODE_ENV` is `production` and Redis still isn't configured, the rate limiter throws outright on every rate-limited request—a request-time backstop behind the startup-time refusal described in tier two above. In the `subscriptions/listen` push mechanism (`mcp-user-event-bus.ts`), without Redis the server falls back to an in-memory event bus that works correctly for a single process but loses cross-instance delivery silently in a multi-instance deployment—no error, just a stream that never gets its update. In grant revocation (`mcp-grant-revocation-channel.ts`), without Redis a revocation only closes local, in-process listeners; a revoked grant's live stream on a different instance would not be closed. Net effect: Redis is optional for a single-instance or local-development embedding, production startup refuses to boot without it, and any multi-instance deployment needs it for correctness even outside of production, not only for the documented rate-limiting behavior.

## URL paths this server owns

An embedding host must cede every path below—routing all of them to this server's handler rather than its own routes.

Checked before session hydration: `GET /health`, `GET /health/ready`, `GET /metrics`, `GET /privacy`, `GET /terms`, `GET /support`, `GET|OPTIONS /.well-known/oauth-authorization-server`, `GET|OPTIONS /.well-known/oauth-protected-resource`, `GET|OPTIONS /.well-known/oauth-protected-resource/mcp`.

Checked after session hydration: `GET /`, `GET /auth/dev/login`, `GET /auth/google/start`, `GET /auth/google/callback`, `POST /auth/sign-out`, `POST /account/connections/revoke`, `POST /account/connections/revoke-all`, `GET /oauth/authorize`, `POST /oauth/authorize/approve`, `POST /oauth/authorize/deny`, `OPTIONS|POST /oauth/register`, `OPTIONS|POST /oauth/token`, `OPTIONS|POST /oauth/revoke`, and `/mcp` (every HTTP method—there is no method filter on this route).

Additionally, `handleApplicationRequest`'s default static-file handling claims `/assets/*` (any path under that prefix) and the single literal path `/favicon.png`—but this is exactly what `createApplicationMount()` turns off (`serveStaticAssets: false`), since an embedding host almost always wants to serve its own static assets under those same conventional paths instead.

## Verification

The claims above were checked, not assumed. From this repository's root, `bun turbo typecheck` and `bun turbo lint` confirm the mount seam, the injectable database client, and the dependency changes described above compile and lint cleanly across every workspace. `bun run audit:documentation` confirms this document itself contains no dead repository paths, no forbidden API references, and no placeholder domains. `packages/database`'s own test script exercises `createDatabaseClient`'s HTTP branch with a real query against the local test database, and its pooled branch with a construction-and-type assertion only—the local Neon proxy is HTTP-only, so the pooled path has no reachable database in that environment. `applications/web`'s own test script exercises the mount handler's static-asset opt-out (by contrasting it against the unmodified handler, which really does serve the favicon) and its `clientAddress` plumbing.
