# Threat Model

This document is the connector-specific threat model required by the roadmap's `SEC-002` item. It names the assets this server protects, the actors who can reach it, the entry points those actors use, the mitigation this repository actually implements for each one (cited against real files and tests, not aspirational), and the residual risk left over—including risk this repository cannot close because the control lives outside it (a deployment platform's TLS termination, a protected GitHub environment, a human's approval inside a host application). Where a claim depends on something outside this repository, that dependency is named explicitly rather than assumed.

It describes the codebase as it stands after `SEC-001`, `SEC-003`, `SEC-004`, `SEC-005`, `CONFIG-001`, `OAUTH-001`, `OAUTH-003`, `AUTHZ-001`, and `FEDAUTH-001`—see `PROGRESS.local.md` and `.roadmap-progress/*.md` for how each of those landed. This document should be revised whenever one of those controls changes; a threat model that describes mitigations the code no longer has is worse than no threat model at all.

## Assets

- **User identity and profile data**: email, name, avatar URL, role, stored in `users` and exposed through `get_user_profile` and the `user://profile` resource.
- **Session credentials**: the browser session cookie (`user_sessions`, hashed at rest via `hash-credential.ts`) and the Google OAuth state/nonce/PKCE-verifier cookies (`google-oauth-single-use-store.ts`).
- **OAuth artifacts**: authorization codes, access tokens, refresh tokens, and client secrets (`oauth_codes`, `oauth_tokens`, `oauth_refresh_tokens`, `oauth_clients`). Every credential-shaped column stores a SHA-256 hash, never the plaintext value—`packages/database/src/schema.ts`'s `accessToken`/`refreshToken`/`sessionTokenHash`/`csrfTokenHash` columns and every write site that populates them.
- **The `/mcp` resource itself**: the tools, resources, and prompts this server exposes, and the authority to invoke them as a specific authenticated user.
- **Rate-limit and abuse-tracking state**: Redis sorted sets and counters (`sliding-window-rate-limiter.ts`, `mcp-concurrency-limiter.ts`) that stand between an attacker and denial-of-service against every endpoint below.
- **The build and deploy pipeline**: the container image, the GitHub Actions workflows that build and publish it, and the Railway deployment it reaches.

## Actors

- **An unauthenticated network client**: anyone who can reach the public HTTPS endpoint, with no credential at all.
- **A malicious or compromised MCP client / hosted connector**: holds a validly issued access token (its own, or one it phished/replayed) and calls `/mcp` within whatever scope that token carries.
- **A malicious website running in a signed-in user's browser**: cannot read cross-origin responses (Same-Origin Policy still applies) but can attempt to trigger state-changing requests (CSRF) or, if this server ran on a shared machine, probe a loopback-bound local instance directly.
- **A registered but adversarial OAuth client**: has real `client_id`/`client_secret` credentials (or a CIMD URL it controls) and tries to exceed the resource, scope, or redirect URI it was granted.
- **An operator or CI credential holder**: has repository write access, GitHub Actions secrets, or Railway deploy credentials; the threat here is compromise or mistake, not malice by the legitimate operator.
- **A third party this server calls out to**: Google's OAuth/OIDC endpoints, a CIMD URL an OAuth client supplies, or (in the container/CI supply chain) an npm registry or GitHub Action.
- **A co-tenant on shared infrastructure**: another process with access to the same Redis instance or Postgres database, in a deployment that doesn't isolate them per application.

## Trust boundaries

### Browser authorization (the OAuth consent flow)

A signed-in user's browser is asked to approve or deny an OAuth client's request. The threat is a forged approval—either a cross-site request that submits the approve/deny form on the user's behalf, or a replay of a previously issued approval.

Mitigation: `authorization-transaction.ts`'s `createAuthorizationTransaction`/`consumeAuthorizationTransaction` bind every approve/deny submission to a one-time, server-issued transaction id and CSRF token, atomically consumed in one `UPDATE ... WHERE ... RETURNING` so there is no check-then-act window for a second submission to race (`SEC-005`). `isTrustedRequestOrigin` (`csrf-protection.ts`) additionally checks `Sec-Fetch-Site`/`Origin` before any form body is even parsed. Every value used to actually mint the authorization code—client id, redirect URI, PKCE challenge, resource, scope—comes from the server-side transaction record, never from the form the browser posted.

Residual risk: this defends the transaction, not the browser. A user who approves a phishing page's OAuth client because the client's display name is convincing has not been protected by anything in this repository—`client-name-validation.ts` blocks control characters and bidirectional-override tricks in that name, not social engineering with an honest name.

### Hosted connector callbacks and the MCP transport boundary

A remote MCP host (Claude, Codex, ChatGPT) or a browser reaches `/mcp` directly. The threats are: a cross-site browser request riding the user's cookies or an ambient bearer token, and the localhost-specific variant of that same attack against a server bound to loopback for local development.

Mitigation, in the order `authenticateMcpUser` (`mcp-routes.ts`) actually applies it—before any request body is read:

- Localhost DNS-rebinding protection (`isDnsRebindingProtectionActive` + `hasValidLocalhostRebindingHeaders`, `packages/mcp/src/localhost-request-validation.ts`): when the request targets a loopback host, both `Host` and (if present) `Origin` must also resolve to a loopback hostname. _This item found and fixed a real inversion here_: the check was previously gated `MCP_CONFORMANCE_MODE && ...`, so it was active only _during_ conformance-mode test runs and provided zero protection during ordinary local development—backwards from the roadmap's explicit requirement. It is now active whenever conformance mode is off, with two deliberate, documented carve-outs: conformance mode itself (synthetic headers a conformance client may legitimately send) and an active Cloudflare tunnel (which legitimately presents a loopback `Host` alongside a genuinely external `Origin`—see the comment on `isDnsRebindingProtectionActive` in `mcp-routes.ts` for the full reasoning and why enforcing it there would 403 every real tunneled request). See `mcp-boundary-controls.integration.test.ts` and `localhost-request-validation.test.ts`.
- Cross-site origin allow-listing (`validateMcpRequestOrigin`, `mcp-origin-validation.ts`): any request carrying a browser `Origin` header not on `MCP_ALLOWED_ORIGINS` (or the literal `null` sandboxed origin) is rejected. A request with no `Origin` at all is allowed—most MCP clients are not browsers and never send one. See `mcp-origin-validation.test.ts`/`mcp-boundary-controls.integration.test.ts`.
- Network- and user-scoped rate limiting, a failed-authentication lockout, and a bounded concurrency slot, all `SEC-003`.
- Bounded request bodies (`bounded-request-body.ts`, `SEC-004`) before the SDK ever parses JSON-RPC.
- Bearer token lookup by SHA-256 hash, RFC 8707 resource-audience check, and `AUTHZ-001` scope enforcement—after all of the above, never before.

_A real, second defect found and fixed while writing this threat model_: `z.coerce.boolean()` (used for `MCP_CONFORMANCE_MODE`, `PROTOKIT_TUNNEL_ACTIVE`, and `MCP_ENABLE_UI_EXTENSION`) calls JavaScript's `Boolean(value)` on the raw environment string, and every non-empty string—including the literal string `"false"`—is truthy. An operator (or `scripts/develop.ts`, which writes `PROTOKIT_TUNNEL_ACTIVE=false` into the spawned dev server's real environment on every non-`--tunnel` run) setting `MCP_CONFORMANCE_MODE=false` was silently _enabling_ it. Both `applications/web/src/environment-schema.ts` and `packages/mcp/src/environment-schema.ts` now parse these fields through a strict `"true"`/`"false"`-only schema that fails validation loudly on anything else, instead of silently coercing. See `environment-schema.test.ts` in both packages.

Residual risk: the DNS-rebinding check's tunnel carve-out means a live Cloudflare tunnel has no rebinding-specific protection of its own; its actual defense is the origin allow-list, which the operator must configure correctly for the tunnel's real callers (documented in the `tunnel` skill, not enforced by code). This is a real, accepted gap, not an oversight.

### Metadata fetching (SSRF)—CIMD today, any future URL-fetching tool tomorrow

Anything this server fetches at a URL an untrusted party supplied is an SSRF surface. Today that is exactly one code path: Client ID Metadata Documents (`client-metadata-documents.ts`, `OAUTH-002`), where an OAuth client's `client_id` is itself an HTTPS URL this server retrieves.

Mitigation: `assertHostnameIsPubliclyRoutable` blocks loopback, RFC 1918, link-local, and cloud-metadata address ranges for both the literal-IP case and the resolved-hostname case (a DNS-rebinding variant of SSRF, not the browser one above), rejects when _any_ resolved address is private, sets `redirect: 'error'` so a redirect cannot be followed to an internal target, and bounds the fetch by timeout and response size. See `client-metadata-documents.test.ts`'s `SSRF protections` suite (loopback literal, cloud-metadata literal, RFC 1918 literal, DNS rebinding, mixed public/private resolution, IPv6 loopback/link-local, DNS failure, and the `redirect: 'error'` wiring itself—nine cases). The HTTPS-only requirement is a second, independent layer against the DNS-rebinding window between the resolve-time check and the actual connection: a rebound name doesn't produce a certificate that validates for it, so the request fails the TLS handshake rather than silently reaching the internal target.

Google's token/userinfo/JWKS fetches (`google-outbound-fetch.ts`, `FEDAUTH-001`) reuse this same bounded-fetch shape independently, but are not SSRF-relevant in the same sense—their target hosts are Google's own fixed, hardcoded constants, never a value supplied by the end user or the OAuth client.

Residual risk, by design and explicit roadmap decision: this server registers no tool today that fetches an arbitrary user-supplied URL (`get_user_profile` and `list_audit_events` are both purely local). The implementation bullet asking to apply SSRF controls "to every future tool that fetches user-controlled URLs" is a standing requirement on whoever adds the next such tool, not something that can be pre-built against a tool that doesn't exist—`token-passthrough.test.ts`'s fetch-spy tests will fail the moment a new tool adds an unguarded outbound fetch, which is the closest a test suite can get to enforcing a not-yet-written control.

### MCP inputs—treated as untrusted, bounded, and schema-validated

Every tool input is Zod-validated against its declared `inputSchema` before a handler ever runs (enforced by the MCP SDK's own dispatch, not something this repository re-implements). Field-level and byte-level bounds exist at every layer a request can be oversized: request bodies (`bounded-request-body.ts`), OAuth field lengths, PKCE syntax, redirect URI counts/lengths (`request-limits.ts`, all `SEC-004`), and bearer tokens (`mcpMaxBearerTokenLength`). A rejected oversized or malformed request performs no database write—verified directly in `oauth-routes.ts`'s tests via `mockInsertedValues` staying empty on every rejection path.

### Tool output, resource content, and prompt-injection boundaries

Everything a tool returns, a resource serves, or a prompt template embeds is content this server generated from its own database—`get_user_profile` echoes back a user's own stored profile fields; `user://profile` does the same; `summarize` embeds a user-supplied `topic` string into a prompt template it hands back to the calling model, never anything fetched from a third party. There is currently no code path in this server that ingests untrusted _external_ content (a fetched web page, another user's data, a third-party API response) and hands it to a model as tool output—the SSRF section above is exactly the boundary that would need to hold if one existed, because the moment a tool fetches an external URL, that response becomes untrusted content a downstream model could be manipulated by instructions embedded in it (classic prompt injection via tool output). Any future tool that fetches external content must treat that content as data, not instructions, and must not use it to justify skipping host-side approval for a sensitive action it triggers.

Result sizes are bounded (`tool-response.ts`'s 256KB cap on generated tool output, `SEC-004`) so a maliciously large response cannot be used to exhaust a client or this server's own memory building it.

### Write and destructive tool approval

MCP's protocol-level mechanism for this is tool annotations (`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`) that a host application reads to decide whether to prompt a human before invoking a tool. This server's entire contribution to that mechanism is making the annotations accurate; the actual approval prompt is host-side behavior this repository cannot implement or verify—a claim about Claude's, Codex's, or ChatGPT's approval UI would be describing a system outside this repository.

What this repository does guarantee: `McpToolAnnotations` is a required (non-optional) field on every tool definition (`types/primitives.ts`, `META-001`), so a tool cannot ship without declaring all four hints, and `metadata-contract.test.ts` asserts a tool can never claim both `destructiveHint: true` and `readOnlyHint: true` at once—a contradiction no host could act on consistently. Today, both registered tools (`get_user_profile`, and the conformance-only `list_audit_events`) are `readOnlyHint: true`/`destructiveHint: false`; _this server has no write or destructive tool at all_, so the acceptance criterion here is trivially satisfied by absence rather than by a tested approval flow. The value of the guard above is entirely in what it prevents the _next_ tool from shipping incorrectly.

### Database-stored tokens

Covered under Assets above: every OAuth credential column and the session-token column store a SHA-256 hash, never the plaintext value (`hash-credential.ts`, applied at every write site in `oauth-routes.ts`, `authorization-transaction.ts`, and `session-authentication.ts`). A database read (via a compromised credential, a misconfigured backup, or a SQL injection this repository's use of Drizzle's parameterized queries is designed to prevent) yields hashes an attacker cannot present as a live credential without also finding a SHA-256 preimage.

Residual risk at the time this item ran: `DATA-001` (not yet run) was the roadmap's owner for credential lifecycle. `DATA-001` has since landed — see the "Residual risks" section below for the current, corrected state rather than this section's original claim.

### Redis

Used for rate-limit/concurrency counters (`SEC-003`), single-use OAuth state (`google-oauth-single-use-store.ts`), and per-user MCP event pub/sub (`mcp-user-event-bus.ts`, `S-11`/`PROTO-002`—each user gets an isolated channel so a published resource-update event cannot cross a user boundary). Redis holds no credential in plaintext and no durable data—every value it stores is either a counter, a short-lived single-use token, or an ephemeral pub/sub message; the source of truth for every credential remains Postgres. Connections are TLS-required and non-`rediss://` URLs are refused in production, alongside a bounded reconnect strategy so an unreachable Redis fails fast instead of hanging every request that touches it indefinitely (`CONFIG-001`, and the `redis-client.ts` defect `SEC-003` found and fixed).

Residual risk: Redis compromise (an attacker with direct network access to it, in a deployment that doesn't isolate it) could forge rate-limit state to look like there's no abuse in progress, or replay a single-use OAuth state token before its TTL if they can write to the exact key. This repository's mitigation is TLS + the requirement above; network-level isolation of the Redis instance is a deployment-platform responsibility, not something this codebase can enforce.

### Reverse proxies and network identity

`trusted-proxy.ts` treats every header-derived client address (`X-Forwarded-For`, `Forwarded`, `CF-Connecting-IP`) as untrustworthy unless the immediate peer's socket address is itself inside a configured trusted-proxy CIDR (`TRUSTED_PROXY_CIDRS`), which defaults to trusting nothing—an unconfigured deployment cannot have its rate limiting or lockout bypassed by header forgery, it just falls back to the raw socket address (`SEC-003`).

Residual risk: this control is only as good as the operator's `TRUSTED_PROXY_CIDRS` configuration on the real deployment platform (Railway, per this template's default target). This repository cannot verify from inside itself that the configured CIDR range actually matches the platform's real edge IP ranges—that verification requires a live deployment, which is out of scope for a repository-level threat model.

### Third-party APIs

The only third-party API this server calls is Google's (`FEDAUTH-001`): PKCE `S256` on the authorization request, a nonce plus full ID-token signature/issuer/audience/`azp` validation against Google's own JWKS (fetched from Google's hardcoded, documented endpoint—Google's discovery document is deliberately never fetched, so a compromised discovery response can never redirect the client-secret-bearing token exchange), single-use state via an atomic Redis claim, and bounded fetches with a timeout, exact host, and response-size cap (`google-outbound-fetch.ts`).

Residual risk: this server trusts Google's identity assertion as the source of truth for "who is this user." A compromise of a user's Google account is a compromise of their protokit account; there is no independent second factor this repository adds on top of Google's own.

## Boundary controls this item added or fixed

- Fixed the DNS-rebinding protection's inverted gating condition (`mcp-routes.ts`'s `isDnsRebindingProtectionActive`) so it is active outside conformance mode, as the roadmap requires, with tunnel and conformance-mode carve-outs documented inline and covered by `mcp-boundary-controls.integration.test.ts`.
- Fixed the `z.coerce.boolean()` mis-coercion of the literal string `"false"` to `true` across every boolean environment flag in `applications/web` and `packages/mcp` (`strictBooleanEnvironmentFlag`), covered by `environment-schema.test.ts` in both packages.
- Made `mcp-origin-validation.ts`'s allow-list parsing an exported pure function (`parseAllowedOrigins`) and its two exported functions accept an optional allow-list parameter, so cross-site rejection can be unit-tested directly instead of only through a process-wide `mock.module('@web/env', ...)`—this file previously had no test coverage of its own at all. See `mcp-origin-validation.test.ts`.
- Added `mcp-boundary-controls.integration.test.ts`: cross-site origin rejection, sandboxed (`null`) origin rejection, and DNS-rebinding rejection, each proven against the real dispatcher (not a mock), each asserting the specific `403`/`forbidden` shape and that the request never reaches the bearer-token authentication branch (which would 401, not 403).
- Added `token-passthrough.test.ts`: asserts `McpContext` never exposes a token-shaped field, and that every currently-registered tool, resource, and prompt handler makes zero outbound `fetch` calls—the regression guard for "never pass connector tokens through to downstream services."
- Added the destructive/read-only annotation-consistency check to `metadata-contract.test.ts`.
- Added `bun run test:security`, wiring the tests above alongside the existing SSRF (`client-metadata-documents.test.ts`) and oversized-body (`bounded-request-body.test.ts`, `resource-exhaustion.test.ts`) coverage this item's verification block names.
- Ran `bun run audit:secrets` (`gitleaks git --no-banner --exit-code 1 --redact`) against the full commit history on this branch: no leaks found. Manually reviewed every `logger.error`/`logger.warn`/`logger.info` call site across `applications/web`, `packages/mcp`, and `packages/database` that logs anything token/secret/credential/code-adjacent; none pass a raw credential value (`oauth-routes.ts`'s refresh-token-reuse log passes only a `familyId`, never the token or its hash, by explicit design already documented inline).
- `OPS-002` / `S-15`: split `GET /health` into a dependency-free public liveness check (`{ status: "ok" }` only) and an authenticated `GET /health/ready` carrying the dependency/topology detail the old endpoint exposed to any caller. The readiness probe is coalesced and TTL-cached (`coalesced-probe-cache.ts`) so a burst of authenticated readiness or metrics traffic cannot multiply real Postgres/Redis connection work. `/metrics` now compares its bearer credential in constant time (`constant-time-equals.ts`, via the shared `bearer-credential-authentication.ts`), is rate-limited on every request (not just failures), sends `Cache-Control: no-store`, and refuses plaintext transport in production — `/health/ready` carries the identical protections. Both routes, plus the three `/.well-known/*` metadata documents, are now dispatched before `hydrateSession` runs, so none of them ever queries session storage even when sent a forged cookie.

## Residual risks explicitly not addressed by this item

Each of these is owned by a specific, separately scheduled roadmap item—named here so this document doesn't imply they're closed:

- **Updated — closed by `DATA-001`, landed the same wave as this item**: newly issued confidential-client secrets now carry a `client_secret_expires_at` (`oauth_clients.clientSecretExpiresAt`) enforced at every authentication call site, not just returned in the registration response; every foreign key in the schema now defines `onDelete: 'cascade'` except `oauth_clients` itself (deliberately, per the per-relationship reasoning in `.roadmap-progress/DATA-001.md`); and `SESSION_SIGNING_SECRET` rotation gained a documented two-step overlap-then-cutover procedure (`SESSION_SIGNING_SECRET_PREVIOUS`, `bun scripts/rotate-secret.ts session` / `session-cutover`) — see `SECRETS-ROTATION.md`. Residual gap that remains even after `DATA-001`: existing rows issued before that item landed have `clientSecretExpiresAt: null` (no retroactive expiration was backfilled), so an operator relying on this control for a pre-existing deployment should force a rotation of every live confidential-client secret rather than assuming the new column alone protects them.
- **Updated — closed by `OBS-001`, landed the same wave as this item**: the `summarize` prompt no longer logs the raw `topic` string by default; `packages/mcp/src/logger.ts` now redacts a named list of credential-shaped keys plus three value shapes (bearer tokens, JWTs, connection strings) anywhere in a serialized log line, and prompt content specifically logs only as `topicLength` unless the explicit, production-refused `LOG_CONTENT_DIAGNOSTICS_UNTIL` diagnostic window is active. See `RUNBOOK.md`'s "What gets logged, and what does not" section for the full policy and `bun run audit:logs` for the static complement that catches a credential interpolated into a free-text log message.
- Whether the real deployment's TLS termination, GitHub environment protection rules, and Railway's deploy-on-push configuration are correctly set cannot be verified from inside this repository at all—those are properties of a live deployment this repository does not control or observe (`OPS-001`, `DEPLOY-001`).
