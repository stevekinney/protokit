# Claude Connector Directory Submission Evidence (`DIST-001`)

This is the evidence package for submitting this server to Anthropic's [Connectors Directory](https://claude.com/docs/connectors/directory). It exists because the roadmap's `DIST-001` gate is deployment-blocked by nature — the directory submission portal and review process require a live public HTTPS host and a human completing a real browser OAuth login against it, neither of which exists inside this repository. This document does the part that does not require those things: it maps every documented requirement to the specific file, test, or command that proves this codebase satisfies it, and states precisely what remains for the operator who deploys this template and submits it.

Every citation below to Anthropic's documentation was fetched directly from the source on 2026-08-20/21, not recalled from training data, per this repository's own "verify every command and API claim against primary documentation" convention. Directory requirements can change — re-fetch these three pages immediately before submitting, exactly as the roadmap's fifth acceptance criterion requires:

- [Submitting to the Connectors Directory](https://claude.com/docs/connectors/building/submission)
- [Pre-submission checklist](https://claude.com/docs/connectors/building/review-criteria)
- [Anthropic Software Directory Policy](https://support.claude.com/en/articles/13145358-anthropic-software-directory-policy)

## What this item added

- `applications/web/src/connector-smoke-inspector.ts` (new) and `bun run test:connector:inspector` (new script) — a ready-to-run MCP Inspector smoke harness, matching the shape `INTEROP-001` established for `test:connector:codex`/`test:connector:claude-code`. It runs the pinned, lockfile-resolved `@modelcontextprotocol/inspector@2.3.0` CLI for real, against a locally self-hosted instance of this server (or a real `--host https://HOST`), and proves two things the pre-submission checklist names directly:
  - Run unauthenticated against `/mcp`, the real Inspector CLI correctly detects this server requires OAuth and refuses to proceed (`--stored-auth-only`, exit code 3, `auth_required`).
  - The exact wire protocol the Inspector CLI speaks (Streamable HTTP via `@modelcontextprotocol/client`'s `StreamableHTTPClientTransport`, the same library the Inspector itself is built on and this repository's own integration tests already drive against this server) lists `get_user_profile` with its `title` and `readOnlyHint: true` annotation intact, and successfully calls it, once authenticated with a real, resource-bound bearer token obtained through this server's real `authorize` → `approve` → `token` chain.
- One real, reproducible finding from building this harness, documented in the file's own header comment rather than hidden: the Inspector CLI's own OAuth-aware transport does not reliably honor a bearer token supplied via `--header` once a server advertises OAuth through `WWW-Authenticate` — it hangs past its own `--connect-timeout` instead of using the supplied token. This is a client-side behavior of the Inspector CLI itself, not a defect in this server (the identical protocol round trip succeeds every time through the official SDK client, proven above). The Inspector CLI's own `--help` documents the realistic non-interactive path for this exact situation — `--use-stored-auth` / `--wait-for-auth` after a human completes OAuth once in a browser — which is what the harness prints as the manual completion step when given `--host`.

Run it:

```sh
bun run test:connector:inspector                          # self-hosts this server locally
bun run test:connector:inspector -- --host https://HOST   # points at a real deployment
```

## Icon and brand assets — a real gap, not fabricated

The submission portal's "Listing" step requires an icon. This repository's only existing icon file, `applications/web/public/favicon.png` (served at `/favicon.png`, referenced from `applications/web/src/views/document.tsx`), is a genuine 0-byte placeholder — confirmed with `file applications/web/public/favicon.png` (`empty`) and `git log` (unchanged since the original Bun+React scaffold commit, `16d9d75`). This repository is an unbranded template ("Bun + React MCP Template" per `README.md`); it has never defined a product name, logo, or color identity anywhere in its documentation (confirmed by grepping `README.md`/`CONNECTORS.md` for `brand`/`logo`/`icon` and finding nothing). Inventing one here would mean fabricating a visual identity for a company that does not exist, which this repository's own conventions and this task's explicit instructions both prohibit. **Operator action**: before deploying a real instance of this template for submission, replace `favicon.png` with a real icon and decide on the product name/branding the submission's "server name" (100 characters max) and "tagline" (55 characters max) fields will use — this cannot be done from inside a generic template.

## Data handling and authentication mode (portal steps not yet reachable)

Two of the submission portal's steps ask questions this repository can answer today, ahead of time:

- **Authentication mode**: OAuth with dynamic client registration and Client ID Metadata Documents (`client_id_metadata_document_supported: true` — `OAUTH-002`), not a static client ID and not a custom/no-auth connection. `authorization_code` and `refresh_token` are the only supported grants; `client_credentials` was deliberately removed (`SEC-001`) and must never be re-added.
- **Data handling**: the underlying API is entirely first-party (this server's own database, fronting Google sign-in for identity only). It does not handle personal health data or sponsored content, and returns no financial or payment data of any kind.

## What remains, precisely (deployment-blocked)

- Deploy the current revision to a production domain (not a tunnel or test endpoint, per the roadmap's own first bullet for this item) and confirm `GET https://HOST/health` returns `{"status":"ok"}`.

- Add this server as a custom connector in the real, hosted Claude product, complete the OAuth flow, and invoke `get_user_profile` — the "custom connector in Claude" half of the pre-submission checklist. Export the conversation or screenshot the successful tool result and the connector's settings page (revision-identifying, credential-free), per `CONNECTORS.md`'s existing manual-procedure section for this exact step.
- Replace the placeholder `favicon.png` with a real icon and decide the product name/tagline for the submission's "Listing" step.
- Set `SUPPORT_CONTACT_EMAIL` in the production environment so `/support` names a real, monitored address instead of rendering "not configured."
- Create and document a real Google test account that has completed this server's OAuth consent screen once against the deployed instance, for the portal's "Test & launch" step.
- Confirm the deployed origin's TLS certificate chains to a recognized certificate authority (Railway's managed certificates do this by default, but this has never been verified against an actual Railway deployment from inside this repository).
- Re-fetch the three primary-source pages linked at the top of this document immediately before submitting, and re-run this evidence pass against whatever has changed.
- Complete the submission portal's seven compliance acknowledgments (directory guidelines, first-party API usage, financial transactions, AI media generation, prompt injection, conversation data collection, public documentation) — all seven are required and are policy attestations only an authorized organization member can make, not something this repository can pre-fill.
